# FBX 3D 모델 파일 대상 바이너리 델타 도구 비교

## 1. 개요

본 문서는 3D 모델 데이터인 **FBX 파일**을 대상으로 `rsync`, `xdelta3`, `bsdiff`의 바이너리 델타 효율을 비교한 결과를 정리한다.

PNG처럼 내부가 압축된 포맷은 작은 시각적 변경도 바이트 수준에서는 넓게 퍼질 수 있어 델타 효율이 낮게 나타날 수 있다. 반면 FBX와 같은 비압축 바이너리 3D 모델 파일은 내부 구조가 비교적 유지되는 경우가 있어, 변경된 일부 구간만 저장하거나 전송하는 델타 방식의 적용 가능성이 있다.

본 비교는 designer_git의 자체 Rolling Hash 기반 delta 엔진을 설계하기 위한 참고 자료이자, 기존 도구 대비 성능을 평가하기 위한 기준선으로 활용한다.

## 2. 실험 환경 및 대상

- **OS / 환경**
  - Windows
  - MSYS2 UCRT64 터미널
  - WSL 환경 병행

- **테스트 데이터**
  - 3D 모델 파일
  - 포맷: FBX
  - 원본 파일: `tree_origin.fbx` 약 72MB
  - 수정 파일: `tree_fix.fbx` 약 73MB
  - rsync 기준 전체 파일 크기: 75,500,748 bytes, 약 75.5MB

- **비교 대상 도구**
  - `rsync`
  - `xdelta3`
  - `bsdiff`

## 3. 실험 과정 및 결과

### 3.1 rsync를 이용한 델타 전송

`rsync`는 파일 동기화 도구이며, 변경된 데이터만 전송하기 위해 rolling checksum 기반의 델타 전송 방식을 사용한다.

- **전체 파일 크기**: 75,500,748 bytes, 약 75.5MB
- **일치한 기존 데이터**: 25,143,072 bytes, 약 25.1MB
- **실제 전송된 데이터**: 50,381,708 bytes, 약 50.3MB

#### 분석

`rsync`는 전체 파일 중 약 25.1MB에 해당하는 기존 데이터를 재사용했다. 이는 전체 파일을 다시 전송하는 방식과 비교했을 때 약 33% 수준의 데이터 재사용이 가능했음을 의미한다.

다만 `rsync`는 본래 버전관리 도구가 아니라 파일 동기화 도구이다. 따라서 커밋 히스토리 저장, 특정 버전 체크아웃, 커밋 메타데이터 관리 같은 VCS 기능은 별도로 제공하지 않는다.

---

### 3.2 xdelta3를 이용한 패치 생성

`xdelta3`는 두 바이너리 파일 사이의 차이를 계산하여 패치 파일을 생성하는 도구이다.

- **생성된 패치 파일**: `tree_fix.xdelta`
- **패치 파일 크기**: 49,571,354 bytes, 약 49.5MB

#### 분석

`xdelta3`의 패치 크기는 `rsync`의 실제 전송량과 유사한 수준으로 나타났다. 이는 FBX 파일 내부의 일부 데이터가 수정 후에도 그대로 유지되어, 전체 파일을 저장하지 않고도 변경분 중심의 표현이 가능했음을 보여준다.

정확한 실행 시간 수치는 별도로 기록하지 않았으나, 실험 과정에서 `bsdiff`에 비해 훨씬 빠르게 패치를 생성했다. 따라서 `xdelta3`는 패치 크기와 처리 속도의 균형 측면에서 실용적인 비교 기준선으로 볼 수 있다.

---

### 3.3 bsdiff를 이용한 패치 생성

`bsdiff`는 바이너리 파일 간 차이를 매우 세밀하게 분석하여 작은 패치 파일을 생성하는 도구이다.

- **생성된 패치 파일**: `tree_fix.bsdiff`
- **패치 파일 크기**: 49,325,224 bytes, 약 49.3MB
- **실행 시간**: 6분 4.7초, 약 6m4.716s

#### 분석

`bsdiff`는 세 도구 중 가장 작은 패치 파일을 생성했다. 그러나 `xdelta3`와의 패치 크기 차이는 약 0.2MB 수준으로 크지 않았고, 70MB대 FBX 파일을 처리하는 데 6분 이상이 소요되었다.

따라서 `bsdiff`는 패치 크기 최적화 측면에서는 장점이 있지만, 빈번하게 수정되는 3D 에셋의 버전관리나 동기화 작업에 적용하기에는 연산 오버헤드가 크다.

## 4. 도구별 비교 요약

| 도구 | 주요 목적 | 결과 크기 / 전송량 | 장점 | 한계 |
|---|---:|---:|---|---|
| `rsync` | 파일 동기화 | 약 50.3MB 전송 | 네트워크 전송량 절감, 동기화에 적합 | 버전 히스토리 관리 기능 없음 |
| `xdelta3` | 바이너리 패치 생성 | 약 49.5MB 패치 | 패치 크기와 처리 속도의 균형이 좋음 | 별도 VCS 기능은 없음 |
| `bsdiff` | 바이너리 패치 생성 | 약 49.3MB 패치 | 가장 작은 패치 크기 | 실행 시간이 매우 김 |

## 5. 결론 및 시사점

실험 결과, FBX 파일은 PNG와 같은 압축 이미지 포맷에 비해 기존 바이너리 구조가 더 많이 유지되어 델타 기반 저장 및 전송의 가능성이 있음을 확인했다. `rsync`는 약 25.1MB의 기존 데이터를 재사용했으며, `xdelta3`와 `bsdiff`는 약 49MB 수준의 패치 파일을 생성했다.

이는 전체 파일을 매번 저장하는 Git LFS 방식과 비교했을 때 의미 있는 절감 가능성을 보여준다. 다만 각 도구의 목적과 장단점은 다르다. `rsync`는 네트워크 동기화에는 적합하지만 버전관리 기능은 제공하지 않으며, `bsdiff`는 가장 작은 패치 크기를 만들지만 실행 시간이 길다. `xdelta3`는 패치 크기와 처리 속도 측면에서 비교적 균형 잡힌 결과를 보였다.

따라서 `xdelta3`와 `rsync`는 designer_git의 자체 Rolling Hash 기반 delta 엔진을 평가하기 위한 비교 기준선으로 활용할 수 있다. 최종적으로는 FBX와 같은 비압축 바이너리 에셋에 대해 전체 파일 저장 대신 변경 블록 중심의 저장 전략이 실용적인지 벤치마크를 통해 검증한다.

---

## 6. designer_git 적용 방향

본 프로젝트의 목표는 기존 도구를 그대로 사용하는 것이 아니라, 3D 디자이너와 게임 개발자를 위한 바이너리 전용 버전관리 흐름을 제공하는 것이다.

따라서 본 비교 결과는 다음과 같이 활용한다.

1. `rsync`, `xdelta3`, `bsdiff`를 기존 바이너리 델타 도구의 기준선으로 사용한다.
2. 자체 Rolling Hash 기반 delta 엔진의 저장 효율과 처리 시간을 기존 도구와 비교한다.
3. FBX처럼 델타 효율이 기대되는 비압축 바이너리 파일을 우선 지원한다.
4. PNG, ZIP, JPG처럼 압축되어 델타 효율이 낮은 포맷은 필요 시 전체 저장 방식으로 fallback한다.

이를 통해 designer_git은 Git LFS처럼 매 커밋마다 전체 파일을 저장하는 방식의 한계를 줄이고, 비압축 바이너리 에셋에 특화된 버전관리 가능성을 검증한다.
