## 1. 게임/VFX 파이프라인과 파일 포맷
 
게임 개발 파이프라인 단계별로 사용하는 파일과 designer-git 적용 가능 여부.
 
| 단계 | 주요 작업 | 파일 | dgit 효율 |
|------|-----------|------|-----------|
| 1. 모델링 | 폴리곤 편집, 형태 제작 | .ma, .mb, .ztl | ❌ 버텍스 전체 변경 |
| 2. 텍스처링 | 픽셀 단위 색상/재질 수정 | **TIFF** (Substance Painter) | ✅ 극소량 99.9% |
| 3. 리깅 | 본 설정, 스킨 가중치 | **FBX** (Blender) | ✅ 본 회전 0.41% |
| 4. 애니메이션 | 키프레임 제작 | FBX, Maya | ❌ 전체 재직렬화 |
| 5. 씬 어셈블리 | 오브젝트 배치, 조명 설정 | USDA | △ 구조적 효율 예상 |
| 6. 최종 배포 | 엔진/웹/앱 에셋 최종화 | **glTF .bin** | ✅ 0.11~0.18% |
 
> glTF는 씬 구조(.gltf JSON) + 메시 데이터(.bin)로 구성.
> 배포 직전 반복 수정되는 .bin 파일이 실험 대상.
 
---
 
## 2. 프로젝트 개요
 
### 문제 정의
Git LFS는 매 커밋마다 파일 전체를 저장 → 커밋 횟수에 비례해 저장소 선형 증가.
designer-git은 변경분(delta)만 저장하여 저장소 증가량을 최소화한다.
 
### 실험 환경
 
| 항목 | 내용 |
|------|------|
| OS | Ubuntu 22.04 (WSL2) |
| 빌드 | g++ 14, C++17, libtiff |
| 반복 횟수 | 3회 반복 (TIFF), 독립 저장소 (FBX/glTF) |
| 사용 에셋 | **Fantasy Knight Girl** (실제 게임 캐릭터 에셋, 리깅 완료, 158개 본) |

## 3. 실험 결과
 
### 3-1. Git LFS vs designer-git 누적 저장소 비교 (TIFF, 10회 커밋)
 
비압축 TIFF(100.69MB)를 10회 커밋 시 누적 저장소 크기.
 
| 커밋 | Git LFS | dgit payload | dgit 전체(.vcs) |
|-----:|--------:|-------------:|----------------:|
| 1 | 100.69 MB | 100.69 MB | 100.69 MB |
| 2 | 201.38 MB | 124.76 MB | 124.76 MB |
| 5 | 503.44 MB | 148.20 MB | 148.20 MB |
| **10** | **1,006.88 MB** | **167.75 MB** | **268.44 MB** |
 
> 10회차 snapshot(복원 성능용, ~100MB) 포함 기준 **73.34% 절감**
> 순수 delta payload 기준 **83.34% 절감**
 
---
 
### 3-2. 수정량별 delta 효율 분석 (TIFF, 3회 반복)
 
| 케이스 | 수정 내용 | 변경 블록 | 저장 방식 | 절감률 |
|--------|-----------|:---------:|:---------:|-------:|
| A 극소량 | 극소량 픽셀 수정 | 2/25 (8%) | **delta** | **99.90%** |
| B UV소량 | UV 기준 소량 수정 | 17/25 (68%) | **delta** | **62.68%** |
| C 중간 | 중간 수정 | 24/25 (96%) | fullcopy | 0% |
| D 전체 | 전체 수정 | 25/25 (100%) | fullcopy | 0% |
 
> fullcopy 전환 임계치: **변경 블록 비율 80%**
> 시각적 수정 면적보다 **UV island 분산도**가 delta 효율의 핵심 변인
 
---
 
### 3-3. FBX 파이프라인별 delta 효율 (Maya vs Blender, 실제 게임 캐릭터)
 
Fantasy Knight Girl 에셋으로 Maya와 Blender에서 각각 9가지 수정 케이스 비교.
 
| 케이스 | 파이프라인 단계 | Maya FBX | Blender FBX |
|--------|----------------|:--------:|:-----------:|
| 버텍스 소량/대량 수정 | 모델링 | 100% | 100% |
| 본 이동 | 리깅 | 100% | **0.41%** ✅ |
| 본 회전 | 리깅 | 100% | **0.41%** ✅ |
| 키프레임 추가/수정 | 애니메이션 | 100% | 100% |
| 오브젝트 이동 | 씬 어셈블리 | 100% | 37.20% |
| 오브젝트 회전 | 씬 어셈블리 | 100% | 30.48% |
| 재질 변경 | 재질 | 100% | **0.35%** ✅ |
 
**원인:**
- Maya FBX: SDK가 런타임 메모리 주소를 ID로 사용 → 매 export마다 전체 변경, 설정 해결 불가
- Blender FBX: Python 자체 구현, 결정론적 ID → 특정 작업에서 delta 가능
---
 
### 3-4. glTF .bin delta 효율 (실제 게임 캐릭터, 18MB)
 
FBX(Maya)가 100% 변경률로 delta 불가임을 확인 후, Blender에서 glTF 분리 형식으로 변환.
git이 처리할 수 없는 **바이너리 메시 파일(.bin)** 에서 delta 효율 검증.
 
```
character_base.bin → character_scene_v2.bin  (케이스 B: 씬 어셈블리)
character_base.bin → character_anim_v2.bin   (케이스 C: 애니메이션 키프레임 수정)
```
 
| 케이스 | 작업 내용 | 원본 크기 | delta 크기 | 변경률 | 절감률 |
|--------|-----------|----------:|----------:|-------:|-------:|
| B 씬 어셈블리 | 오브젝트 X=100 이동 | 18MB | 20K | 0.11% | **99.9%** |
| C 애니메이션 | 30프레임 본 회전 키프레임 추가 | 18MB | 32K | 0.18% | **99.8%** |
 
> 씬 어셈블리(오브젝트 이동)는 transform 값이 .gltf JSON에만 기록 → .bin 변경 최소
> 애니메이션 키프레임 데이터는 .bin에 저장 → 소량 delta 발생
 
---
 
### 3-5. TIFF 자동 압축 해제 구현 결과
 
Substance Painter 기본 export = ZIP 압축 TIFF. 기존에는 수동 압축 해제 필요.
 
| 방식 | 워크플로우 | delta 결과 |
|------|-----------|-----------|
| 수동 압축 해제 | SP export → 수동 해제 → dgit add | 0.10MB (99.9%) |
| **자동 압축 해제** | **SP export → dgit add (끝)** | **0.32MB (자동 처리)** |
 
> 엔진이 TIFF 헤더의 compression tag를 읽어 자동 감지 후 비압축 변환
